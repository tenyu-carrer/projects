# 062-D｜WordPressの記事制作を自動化する方法

**状態：初稿／下書き自動保存の流れ図・順番待ち表CSV付き。実際のサイトへの接続・投稿は未検証**  
対象：WordPressでブログを書いていて、記事を入れる作業（貼り付け・見出し・カテゴリ設定など）に時間がかかっている初心者｜所要：約4〜6時間（試験記事1本を下書きとして自動で入れるまで）｜更新日：2026-11-01  
前提：061の記事の作り方、HTTPS（鍵マーク付き）で表示される自分のWordPressサイト、管理者の権限。追加課金、有料API、有料の記事自動作成サービスは使いません。

## 1｜到達点と完成物

この講座のゴールは、**記事づくりを「機械に任せる作業」と「人が見る作業」に分け、記事を下書きとしてWordPressへ自動で入れ、人が確認してから予約公開する流れを作れるようにする**ことです。

完成物は、①設計シート、②作業の分担表、③下書きの順番待ち表、④アプリケーションパスワード（専用の合鍵）の設定記録、⑤下書きを1本入れる仕組み、⑥誤公開・漏れの点検記録、⑦人の確認記録、⑧公開前チェック記録の8点です。

付属見本は、架空の「駅前の小さな学習塾」の流れ図と、下書きの順番待ち表です。実際のサイトへの接続や投稿ではありません。

**完成条件：** 仕組みが記事を「下書き」としてだけ入れ、公開は人が管理画面で行い、順番待ち表のすべての予約済みの行に確認者と確認日がある。

## 2｜この講座で使う言葉

- **下書き（draft）**：WordPressに保存されているが、まだ公開されていない記事。
- **REST API（レストエーピーアイ）**：WordPressの外から、決まった形で記事を出し入れするための窓口。WordPressに最初から付いています。
- **アプリケーションパスワード**：外の仕組み専用の合鍵。ログイン用のパスワードとは別で、いつでも取り消せます。WordPressの公式資料では、HTTPSのサイトで使える機能と説明されています。
- **順番待ち表**：記事ごとの状態（設計中・下書き保存済み・確認待ち・予約済み・公開済み）を並べた表。
- **権限**：WordPressのユーザーごとにできること（投稿者・編集者・管理者など）。

## 3｜どこまで自動にするか

「記事を全部自動で作って、自動で公開する」仕組みは作りません。理由は3つです。

- 061で学んだとおり、AIの下書きには、まちがった数字や体験のない一般論が混ざる
- 確かめていない記事が自動で公開されると、読者が困り、直すのも大変
- 中身の薄いページを大量に作ることは、Googleのスパムに関する方針（大量生成されたコンテンツの不正使用）に触れるおそれがある

この講座で自動にするのは、**記事をWordPressへ入れる手間**です。見出しの整え、カテゴリやタグの設定、抜粋の入力など、毎回同じ作業を機械に任せ、**事実・体験・公開は人**が受け持ちます。

## 4｜作業を分ける

```text
私のWordPress記事づくりの作業【今の手順】を、「機械に任せる」「人が見る」に分けて表にして。公開と事実の確認は人にして。
```

見本の学習塾では、次のように分けました。

| 作業 | 担当 |
|---|---|
| 見出しと下書きを作る | AI（ChatGPTの画面で人が頼む） |
| 体験を書く・事実を確かめる | 人 |
| タイトル・本文・抜粋・カテゴリ・タグをWordPressへ入れる | 仕組み（下書きとして） |
| 管理画面で読み直す・画像を入れる | 人 |
| 予約公開・公開 | 人 |

AIの部分は、月額プランのChatGPTの画面で人が頼みます。有料APIで記事を自動生成する仕組みは、この講座では作りません。

## 5｜順番待ち表を作る

```text
下書きの順番待ち表の欄を作って。記事番号・タイトル・状態・下書きを入れた日・確認者・確認日・公開予定日・メモ。状態は「設計中／下書き保存済み／確認待ち／予約済み／公開済み」。
```

付属の `062-draft-queue.csv` のように、表計算で作ります。**状態が一目で分かること**が大切です。確認者と確認日が空の行は、予約に進めない約束にします。

## 6｜専用の合鍵（アプリケーションパスワード）を作る

WordPressの管理画面の「ユーザー」→自分のプロフィールの下のほうに、「アプリケーションパスワード」の欄があります（HTTPSのサイトで表示されます）。

1. 新しいアプリケーションパスワードの名前を付ける（例：「下書き保存用」）
2. 表示されたパスワードを、**その場で安全な場所に保管**する（あとで同じものは表示されません）
3. 仕組みの中には直接書かず、パソコンの「環境変数」などから読み込む
4. 使わなくなったら、同じ欄から取り消す

**ログイン用のパスワードは、仕組みに渡しません。** 可能なら、記事を入れるためだけのユーザー（投稿者など、必要な権限だけ）を作り、そのユーザーの合鍵を使います。

## 7｜下書きを1本入れる仕組み

```text
WordPressのREST APIで、記事を「下書き（status=draft）」として1本だけ保存する短いスクリプトの例を、Pythonで書いて。アプリケーションパスワードはコードに直接書かず、環境変数から読むようにして。公開（publish）はしないで。
```

WordPressのREST APIの記事の窓口では、記事の状態として publish（公開）、future（予約）、draft（下書き）、pending（レビュー待ち）、private（非公開）が選べます。この講座の仕組みは、**必ず draft だけ**を使います。

最初は、中身が「試験記事」とだけ書かれた記事を1本入れ、管理画面の「投稿」一覧に下書きとして表示されることを確かめます。うまくいったら、試験記事は削除します。

## 8｜仕組みを点検する

```text
このスクリプト【】を読んで、誤って公開してしまう所、パスワードが漏れる所、同じ記事を2回入れてしまう所がないか点検して。
```

AIが作ったスクリプトは、そのまま信じず、次を人が確かめます。

- 状態が draft 以外になっていないか
- パスワードがコードや画面の表示、共有するファイルに残っていないか
- 同じ記事を2回入れないよう、順番待ち表の状態を「下書き保存済み」に変えているか
- 失敗したとき、黙って止まらず、何が起きたかを表示するか

## 9｜人が確認して予約する

```text
下書き【】を読んで、事実（数字・値段・日付）と、体験を足すとよい場所を表にして。確認先は空けておいて。
```

下書きが入ったら、人が管理画面で読み直します。

1. 061の公開前チェックを通す（体験・事実・言い回し）
2. 画像を入れる（自分で撮ったもの、使ってよい素材だけ）
3. 順番待ち表に確認者と確認日を書く
4. 管理画面で予約公開の日時を決める

予約や公開のボタンは、人が押します。

## 10｜運用のルール

```text
下書きの順番待ち表【】を見て、確認者が空のまま予約に進んでいる行、公開予定日が重なっている行を指摘して。
```

- 下書きを一度にたくさん入れない（人が確認できる数だけ）
- 公開予定日を詰めすぎない
- 合鍵の名前と作った日を記録し、半年に1回見直す
- サイトの更新（WordPress本体・プラグイン）のあとは、試験記事で動作を確かめる

## 11｜権利と安全

- 合鍵は、メールやチャットで送らない。漏れたと思ったらすぐ取り消す
- 他人の記事・画像を下書きに入れない
- 頼まれて書く記事は、広告であることを分かるようにする（ステルスマーケティングにしない）
- 他人のサイトに仕組みをつなぐときは、持ち主の許可を取り、合鍵は持ち主に作ってもらう

## 12｜見本で通し練習：学習塾の記事が予約されるまで

付属の `062-draft-queue.csv` を使います。

1. **分担**：4章の表のとおりに分けました。
2. **順番待ち表**：3本の記事を「設計中」で登録しました。
3. **合鍵**：記事を入れるためだけの投稿者ユーザーを作り、その合鍵を作った設定です。
4. **試験記事**：「試験記事」とだけ書いた1本が下書きとして入ったことを確かめ、削除しました。
5. **下書き**：1本目の記事を下書きとして入れ、状態を「下書き保存済み」にしました。
6. **確認**：塾長が読み直し、AIが書いた「必ず成績が上がる」を消し、確認者と確認日を書いてから予約しました。

## 13｜よくある質問

**Q. プログラムが書けなくてもできますか？**  
A. AIに短いスクリプトを書いてもらい、8章の点検をすれば始められます。不安な場合は、まず4〜5章の「分担」と「順番待ち表」だけでも、記事づくりはかなり整います。

**Q. 自動で公開まですれば、もっと楽では？**  
A. 楽ですが、確かめていない記事が出るおそれがあります。この講座では、公開は人が押すことにしています。

**Q. WordPress.comのサイトでも使えますか？**  
A. 使える機能はプランやサイトの種類で変わります。使う前に、自分のサイトの管理画面と公式の資料で確認してください。

## 14｜自動化と収益化（第3段階）

- **固定する作業**：分担表→下書きの材料づくり→順番待ち表→下書きを入れる→誤公開・漏れの点検→事実の抜き出し→予約前の点検→月のふり返り。Cの8プロンプトと仕組みを同じ順で使えば、記事を入れる手間を毎回減らせます。
- **人がやる作業**：体験を書くこと、事実の確認、画像、確認者と確認日の記入、予約・公開。
- **仕事にする場合**：お店や教室のブログの「下書きを入れる仕組み」と順番待ち表を整える手伝いが考えられます。合鍵はお店の人に作ってもらい、こちらはパスワードを預からない約束にします。公開の判断はお店の人が行います。

検索順位・アクセス数・売上・依頼数を保証しない教材です。

## 15｜課題（3段階）

1. **練習**：作業を10個書き出して分担を決める（合格：公開・事実・体験が人）
2. **実用品**：順番待ち表と合鍵を作り、試験記事を下書きとして1本入れる（合格：管理画面で下書きと表示され、公開されていない）
3. **公開想定**：本物の記事を下書きで入れ、人が確認して予約する（合格：確認者と確認日がある）

## 16｜よくある失敗と直し方

1. **自動で公開してしまう**：状態を draft に固定する。
2. **ログイン用パスワードを使う**：アプリケーションパスワードにする。
3. **合鍵をコードに書く**：環境変数から読む。
4. **合鍵をチャットで送る**：送らない。漏れたら取り消す。
5. **同じ記事を2回入れる**：順番待ち表の状態を変える。
6. **一度に大量に入れる**：確認できる数だけ。
7. **確認者が空のまま予約**：予約に進めない。
8. **管理者の権限で動かす**：必要な権限だけのユーザーにする。
9. **更新後に動かなくなる**：試験記事で確かめる。
10. **試験記事を消し忘れる**：確かめたら削除する。
11. **他人のサイトに無断でつなぐ**：持ち主の許可を取る。
12. **AIの下書きをそのまま予約**：061の公開前チェックを通す。

## 17｜公開前チェック、公式情報、限界

- [ ] 作業の分担表で、公開・事実・体験が人になっている
- [ ] 仕組みは draft（下書き）だけを使う
- [ ] ログイン用パスワードを仕組みに渡していない
- [ ] 合鍵はコードや共有ファイルに書いていない
- [ ] 必要な権限だけのユーザーで動かしている
- [ ] 試験記事で動作を確かめ、削除した
- [ ] 予約済みの行すべてに確認者と確認日がある
- [ ] 061の公開前チェックを通した
- [ ] 他人の記事・画像を使っていない
- [ ] 広告の表示が必要な記事には付けた

確認した公式情報：[WordPress REST API ハンドブック](https://developer.wordpress.org/rest-api/)、[WordPress REST API「Posts」](https://developer.wordpress.org/rest-api/reference/posts/)（記事の状態に publish・future・draft・pending・private があること）、[Application Passwords: Integration Guide](https://make.wordpress.org/core/2020/11/05/application-passwords-integration-guide/)（HTTPSのサイトで使えること）、[Google 検索セントラル「スパムに関するポリシー」](https://developers.google.com/search/docs/essentials/spam-policies)、[消費者庁「ステルスマーケティング」](https://www.caa.go.jp/policies/policy/representation/fair_labeling/stealth_marketing/)（確認日：2026-11-01）。

## A/B/C/Dの役割と次の一歩

- **A｜無料体験**：記事づくりの作業を人と機械に分ける。
- **B｜完成見本**：下書き自動保存の流れ図と順番待ち表を読む。
- **C｜再利用できる道具**：設計シートと8プロンプトで、分担から月のふり返りまで回す。
- **D｜作り方講座**：記事を下書きとして自動で入れ、人が確認して予約公開する流れを作る。
